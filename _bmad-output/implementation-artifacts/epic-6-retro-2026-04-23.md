## Successes

1. **Pre-epic 6-0 structure proved the pattern** — Five debt stories before any feature work. By the time 6-1 started, the foundation was clean. Feature stories had fewer review surprises than earlier epics. Pattern confirmed: invest in structural cleanup first.

2. **Party-mode validation caught a critical bug in 6-4** — `show_folder_missing` was missing a `pair_id` guard. Without it, selecting any pair while a different pair had a missing folder would have contaminated the detail panel. Caught before shipping.

3. **Engine-side validation in 6-2** — Validation runs in the engine's `add_pair` handler, not the UI. Prevents TOCTOU race where two dialogs add overlapping pairs simultaneously. The dev understood the architectural reason, not just the rule.

4. **6-0e as a dedicated pure-test story** — No production code changes. Coverage treated as a first-class deliverable with its own story.

5. **6-5 drain decision table** — Disciplined pause to fix correctness before moving to packaging. Found 5 real patches in review. The decision to stop and fix was correct.

6. **Jeremy's BMAD night automation** — Automated BMAD workflow steps running overnight, freeing time for manual testing. Compounding leverage heading into Epic 7's distro validation matrix.

7. **Story 2-12 completed** — The Unified Queue Drainer Refactor (deferred since Epic 3) is done. Three-producer, single-consumer architectural model now in place. Largest structural debt item closed this project has seen.

## Challenges

1. **`mkdirSync` guard missed in three config functions** — `writeConfigYaml` had the guard. `removeFromConfigYaml` (Story 6-3 review), `updatePairPathInConfigYaml` (Story 6-4 review AND party-mode) both missed it. Same defensive pattern, three separate implementations, three chances to miss one step. Root cause: no shared `atomicWriteConfig()` helper in `config.ts`. Convention-enforced invariant instead of structure-enforced.

2. **Stale state cleanup on pair removal (6-3)** — `_sync_pair_rows` and `_pairs_data` not cleared in `on_pair_removed`. Review caught both. Same class of problem: multiple data structures must be kept in sync manually; easy to miss one.

3. **`[Decision]` items left without explicit verdict** — 6-0a's `attempt_count` optional-vs-required review finding was marked `[ ]` (unclosed). Dev resolved it correctly in completion notes, but the review finding had no explicit verdict line. If the outcome had been genuinely ambiguous, there would be no paper trail.

4. **Post-patch rebuild step not documented** — Jeremy created use case tests after a fix was applied, but the package wasn't regenerated. Tests ran against stale artifacts and had to be recreated. The rebuild step (run full build before executing tests after any patch) is a mandatory workflow step that exists nowhere in writing.
